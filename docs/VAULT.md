# Хранилище секретов и бумажный код

## Как это устроено
```
мастер-ключ (32 случайных байта) ─ шифрует все секреты (AES-256-GCM)
  ├─ обёрнут ключом из ПАРОЛЯ (scrypt)          — повседневная разблокировка
  └─ обёрнут ключом из БУМАЖНОГО КОДА (256 бит) — аварийное восстановление
```
На диске нет ни значений секретов, ни их имён. Файл: `~/.jura/jura.vault`.
Этот же главный ключ шифрует журнал, задачи, память и копии (`docs/adr/0008-key-hierarchy-and-encryption.md`).

## Почему «бумажка» — это восстановление, а не ежедневный ключ
Ключ из 256 бит — это 55 символов. Вводить их при каждом запуске нереально, а ключ на бумаге, который
ты вводишь руками каждый день, рано или поздно окажется в файле, фото или буфере обмена. Поэтому:
**пароль — для каждого дня (вводится один раз при запуске `shell`), бумага — на случай «всё пропало»**. Сама бумага защищает даже при полном взломе:
кода нет ни на одном устройстве.

## Создание
```
python -m jura init
```
1. Придумай пароль (от 12 символов, лучше фраза из нескольких слов).
2. Программа покажет код вида `ABCDE-FGHIJ-…` — **один раз**.
3. Перепиши **от руки**. Не фото, не облако, не заметки, не файл.
4. Введи код обратно — программа проверит, что ты записал верно (в коде есть контрольная сумма).
5. Сделай **две копии**, храни в **разных местах**.

## Учения (раз в квартал)
```
python -m jura vault-check-recovery
```
Введи код с бумаги. Если «✓ подходит» — всё в порядке. Код, который ни разу не проверяли, это не резервная копия.

## Что делать, если…
| Ситуация | Действие |
|---|---|
| Забыл пароль | `unlock_with_recovery` по бумажному коду, затем сменить пароль |
| Потерял бумагу, пароль помнишь | Разблокировать паролем и выпустить новый код (`rotate_recovery_code`); старый перестанет работать |
| Потерял и то, и другое | Данные не восстановить никому, включая нас. Секреты придётся выпустить заново |
| Бумагу могли увидеть посторонние | Немедленно выпустить новый код; старый станет недействительным |

## Ограничения
Пока хранилище разблокировано, секреты находятся в памяти процесса. Вредоносный код на той же машине мог бы
их прочитать — поэтому Core должен жить на отдельной машине (см. `THREAT_MODEL.md`).
