# Как J.U.R.A. работает под паролем

## Три способа «оперировать» программой — от лучшего к худшему

| Способ | Как | Надёжность | Когда |
|---|---|---|---|
| **1. API / OAuth** | Официальный интерфейс сервиса; в хранилище лежит токен или ключ | Высокая | Всегда, когда есть: Gmail, Calendar, GitHub, Binance, Spotify |
| **2. Браузер** | Видимое окно Chromium, J.U.R.A. вводит логин и пароль и кликает (Playwright) | Средняя: сайты меняют вёрстку, ставят капчу и 2FA | Когда у сервиса нет API |
| **3. Окна приложений** | Управление интерфейсом настольных программ | Низкая | В последнюю очередь |

**Про Spotify.** Для управления музыкой правильно использовать официальный API (OAuth-токен), а не пароль: Spotify может блокировать
автоматические входы капчей. Вход по паролю подходит как проверка механизма, а рабочая интеграция будет через API (следующая фаза).

## Как устроена безопасность работы под паролем
1. **Модель пароль не видит.** Она называет только имена («секрет demo», «сайт мойсайт»). Подставляет учётные данные код инструмента,
   в момент действия, из зашифрованного хранилища.
2. **Адрес входа берётся из профиля сайта**, а не из аргументов вызова. Обманутая модель (например письмом с «инструкцией»)
   не сможет отправить пароль на чужой адрес.
3. **Только https.** `http.basic_check` редиректы не выполняет вовсе. `web.login` (браузер) редиректам следует, поэтому перед КАЖДЫМ вводом и кликом
   сверяет фактический origin страницы (схема + хост + порт) с адресом профиля и `allowed_origins`; на чужом адресе — отказ до ввода пароля.
4. **По умолчанию всё запрещено.** Возможность включается командой `policy enable …` с повторным вводом пароля; всё пишется в журнал.
5. **L2 (вход, отправка) — только после твоего «да»**, и в вопросе показаны инструмент и аргументы. Подтверждение действует только для этого вызова.
6. **L3 (деньги) консоль не подтверждает**: нужен Face ID на телефоне (появится позже).
7. **Сообщения об ошибках очищаются** от паролей; неизвестные исключения прячутся целиком.
8. **Брокер учётных данных.** Коннектор читает секреты только через `CredentialBroker`: у каждого свой шаблон имён (`web.login` — `ИМЯ.username/.password` и `site.ИМЯ`; `http.basic` — `ИМЯ.username/.password`), служебные записи закрыты, каждое чтение пишется в журнал. Ключи API (`binance.api_key`, `anthropic.api_key`) этими коннекторами не читаются.
9. **Использование паролей = повторный ввод пароля хранилища** при каждом запуске, даже если действие «обратимое».
10. **Результат помечен**: зона, доверие, источник (`ToolResult`). Письмо или страница не станут «обычным текстом».

## Как добавить новый коннектор (для разработки)
1. Файл в `adapters/connectors/` с функцией `make_tools(get_secret, …)`; импортирует только `contracts`.
2. `ToolSpec`: имя, **риск**, `capability` — задаются в коде, а не моделью.
3. Секреты — только через `get_secret(...)` внутри обработчика; безопасные сообщения — через `ToolUserError`.
4. Тесты: локальный сервер или поддельный драйвер, проверка «пароль не в результате, не в журнале, не на диске».
5. Регистрация в `Session._assemble` через `broker.getter_for(...)` со своим шаблоном имён. Возможность по умолчанию **выключена**.
6. Если инструмент использует пароли — `uses_credentials=True`. Метки результата — `result_zone`/`result_trust` в `ToolSpec`.
