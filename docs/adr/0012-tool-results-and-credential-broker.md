# ADR-012 — Метки результатов инструментов и брокер учётных данных
**Статус:** Accepted (реализовано в v0.5; результат внешнего ревью)

## Контекст
1. `ToolPort` возвращал `Any`: после `gmail.read()` система уже не знала, что результат — зона P, недоверенный, из почты.
   Taint терялся, а рантайм мог передать результат облачной модели.
2. Коннекторы получали `vault.get` целиком и теоретически могли прочитать любой секрет по имени.

## Решение
- **`ToolResult(data, zone, trust, source)`** — один небольшой dataclass. `ToolPort` всегда возвращает его. `ToolSpec` задаёт минимальные
  метки (`result_zone`, `result_trust`; по умолчанию **P и недоверенное**); обработчик может сделать их строже, но не мягче
  (`as_result`: зона — максимум, доверие — наихудшее). Метки пишутся в журнал (без данных).
- **`CredentialBroker`** — тонкий слой в ядре: `getter_for(connector, шаблон_имён)` отдаёт функцию, читающую только имена, целиком подходящие под
  шаблон; служебные записи (`__*`) закрыты всегда; каждое чтение (и отказ) — событие `credential.used` / `credential.denied` без значений.
- **`uses_credentials`** в `ToolSpec`: подтверждение — повторный ввод пароля хранилища (уровень PASSPHRASE), даже для L1.

## Альтернативы
- Большая система «безопасных значений» (taint-типы по всему коду): избыточно сейчас; один dataclass достаточен.
- Брокер с выдачей одноразовых токенов и изоляцией процессов: нужен перед сторонними плагинами (ADR-007), не раньше.

## Последствия
- Диалоговое ядро (Phase 1) обязано строить `ModelRequest.zone` из `max_zone` меток данных и сохранять `trust`.
- Защита брокера — от ошибок и чужих плагинов, не от злонамеренного кода внутри ядра. Ключи API хранить под именами,
  не подходящими под шаблоны коннекторов (`binance.api_key`, а не `binance.password`).
- Остаётся: `http.basic_check` берёт адрес из аргумента (защита — подтверждение, где виден адрес).
