# ADR-008 — Иерархия ключей, шифрование данных и резервные копии
**Статус:** Accepted (реализовано)

## Контекст
Требование владельца: если утекла база, взломана программа или украден компьютер, данные для посторонних —
набор символов; расшифровать можно только ключом, записанным на бумаге, но вводить его каждый раз нельзя.

## Решение
**Ключи.**
```
бумажный код (256 бит) ─┐
пароль (scrypt) ────────┴─► главный ключ  — хранится в jura.vault только в зашифрованном виде,
                                            в памяти — только пока Core разблокирован
                                ├─ HKDF("log")        события журнала
                                ├─ HKDF("tasks")      названия задач
                                ├─ HKDF("memory.O/P/S1") память по зонам
                                ├─ HKDF("backup")     резервные копии
                                └─ (сам Vault)        секреты S2 одним зашифрованным блоком
```
- Повседневно: пароль вводится **один раз при запуске** (`shell`). Бумага — только если потеряно остальное.
- Шифр: **AES-256-GCM**, случайный nonce на запись, формат `J1 | nonce | шифротекст+тег`. Любое изменение бита → `DecryptionError`.
- **Привязка к месту (AAD):** в шифротекст входит «адрес» записи (`memory:<id>:content`, `event:<seq>:payload`),
  поэтому перенос шифротекста в другую запись обнаруживается.
- **Строгий режим:** если шифр задан, открытый текст в поле считается подменой файла и отвергается
  (исключение — старые события журнала: их защищает цепочка хэшей).
- **Журнал:** хэш цепочки считается по шифротексту ⇒ целостность проверяется **без ключа**.
- **Копии:** один файл `.jurabak`: [встроенный файл хранилища] + [архив баз, запечатанный ключом "backup"].
  Для восстановления нужны **только этот файл и бумажный код** (или пароль). Проверяются хэши файлов и якорь журнала.

**Что остаётся видимым** (осознанный компромисс): номер, время и вид события, исполнитель, состояние задачи,
зона и время записи памяти, размеры файлов. Не видно: тексты, значения, названия задач, имена секретов,
имена инструментов, содержимое событий.

## Что изменилось по сравнению с первоначальным планом
Планировался отдельный ключ данных на каждую запись («забыть = удалить ключ»). **Отказались**, потому что:
1. журнал по ADR-002 не содержит значений — стирать в нём нечего;
2. для памяти «забыть» = удалить строку; стереть данные из уже сделанных копий нельзя ни одной схемой — только срок хранения копий;
3. усложнение не даёт защиты от тех угроз, которые мы закрываем.
Формат `J1` и префикс `enc1:` позволяют добавить ключи на запись позже, не ломая данные.

## Альтернативы
- **SQLCipher** (шифрует файл БД целиком, скрывает и метаданные): лишняя нативная зависимость; можно вернуться позже.
- **Шифрование диска** одним BitLocker: защищает выключенный компьютер, но не утечку файла и не копии. Включаем **дополнительно**.
- **restic** для копий: зрелый, но вторая зависимость; пока хватает своего формата (собирается в памяти). Вернёмся при росте данных или при облаке.

## Последствия
- Поиск по памяти расшифровывает подходящие по зоне записи в оперативной памяти (для личного объёма достаточно).
- Смена главного ключа (ротация) потребует перешифровки всего — отдельный инструмент, не сделан.
- Пока Core разблокирован, ключ в памяти процесса: вредоносный код на той же машине его достанет.
  Отсюда требование: Core на отдельной машине (Phase 2).
- Старый формат: если `jura.db`/`memory.db` создавались ДО шифрования, незашифрованные записи памяти будут отвергнуты —
  такие базы нужно удалить или мигрировать (на момент релиза реальных данных в них не было).
